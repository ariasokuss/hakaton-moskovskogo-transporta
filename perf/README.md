# Замеры производительности

**Условия.** Контейнер бэкенда ограничен **2 vCPU / 2 ГБ RAM** (`docker-compose.yml`), как в нефункциональных
требованиях ТЗ; PostgreSQL — 1 vCPU / 1 ГБ. JVM: ZGC, `MaxRAMPercentage=75`. Сборка после интеграции ML
(прогон `ml-20260926_1142`, миграции V7–V8).

Стенд: Docker Desktop на Windows-ноутбуке. Нагрузочный клиент работает в той же docker-сети и делит с сервисом
одну виртуальную машину, поэтому цифры **занижены** относительно выделенного сервера.

## 1. Смешанный сценарий — основной замер (26.09.2026)

Разные запросы, а не один URL (иначе это 100% попаданий в кэш главного экрана):
45% главный экран на случайную дату ноября–декабря со случайными коэффициентами, 25% прогноз по маршруту
на горизонт день / месяц / год, 15% прогноз по остановке, 10% зоны внимания, 5% выгрузка CSV за месяц —
2 199 уникальных URL ([`gen_targets.py`](gen_targets.py) → [`targets-mixed.txt`](targets-mixed.txt)).
Клиент — [vegeta](https://github.com/tsenart/vegeta) с фиксированной частотой, 30 с на ступень, после прогрева JIT.
CPU — среднее по `docker stats` за ступень, **200% = оба выделенных ядра**.

| Нагрузка | p50 | p95 | p99 | Успешно | CPU бэкенда, среднее (из 200%) | RAM |
|---:|---:|---:|---:|---:|---:|---:|
| 200 RPS | 1.3 мс | 2.2 мс | 2.8 мс | 100% | 22% | 1.71 ГБ |
| 800 RPS | 0.8 мс | 1.6 мс | 2.1 мс | 100% | 47% | 1.71 ГБ |
| **1 500 RPS** | **1.0 мс** | **3.0 мс** | **25 мс** | **100%** | **98% (49% от 2 vCPU)** | 1.71 ГБ |
| **2 500 RPS** | **1.3 мс** | **102 мс** | 4.0 с | **100%** | **135% (68% от 2 vCPU)** | 1.72 ГБ |
| 3 000 RPS | 38 мс | 219 мс | 3.8 с | 99.2% | 177% (89%) | 1.72 ГБ |
| 3 500 RPS | 1.1 с | 6.3 с | 7.5 с | 70% | 200% — насыщение | 1.72 ГБ |

**Вывод для ТЗ** («сотни RPS при p95 < 200–300 мс, CPU 60–80%, RAM без swap»):

- **1 500 RPS — с запасом:** p95 3 мс, p99 25 мс, CPU 49% двух ядер, ноль ошибок;
- **2 500 RPS — в требовании ТЗ по p95 и CPU:** p95 102 мс при CPU 68%, ноль ошибок, но хвост p99 уже секунды —
  это начало насыщения одного контейнера;
- **≥ 3 000 RPS — предел** одного контейнера: дальше горизонтальное масштабирование (инстансы stateless).

RAM стабильна: 1.7 ГБ из 2 ГБ под любой нагрузкой (куча JVM — 75% лимита), swap контейнеру не выделен.
Разброс между прогонами на ноутбуке заметный: в предыдущем прогоне (модель 1011) на 2 500 RPS было p95 60 мс, p99 172 мс.

Сырой вывод — [`mixed-steps.txt`](mixed-steps.txt).

## 2. Один URL, максимальная пропускная способность

[hey](https://github.com/rakyll/hey), 50 параллельных соединений, 20 с, клиент без gzip.

## 3. Что дало производительность

1. **Прогноз не в горячем пути.** Модель считается заранее; запрос читает неизменяемый снимок из памяти, в БД не ходит.
2. **Мемоизация главного экрана.** Снимок неизменяем → ответ при тех же параметрах тот же. Кэш привязан к снимку
   и сбрасывается сам при новом прогоне.
3. **Кэш готовых байтов.** Главный экран — 24 КБ JSON (3.7 КБ в gzip): сериализация и сжатие не повторяются.

История замеров (25–26.09, до интеграции ML и на перегруженной машине): 243 → 551 RPS на главном экране
после кэша готовых байтов — [`first-run.txt`](first-run.txt), [`dashboard-cached.txt`](dashboard-cached.txt),
[`dashboard-bytes-cached.txt`](dashboard-bytes-cached.txt).

## 4. Воспроизвести

```bash
docker compose up -d
curl -s localhost:8080/api/stops > /tmp/stops.json
python perf/gen_targets.py http://backend:8080 /tmp/stops.json > perf/targets-mixed.txt   # уже лежит в репозитории
bash perf/run_mixed.sh "" 200 800 1500 2500 3500                                          # смешанный сценарий по ступеням

NET=$(docker inspect -f '{{range $k,$v := .NetworkSettings.Networks}}{{$k}}{{end}}' tram-backend)
docker run --rm --network $NET williamyeh/hey -z 20s -c 50 "http://backend:8080/api/dashboard?date=2025-11-08"
```

## 5. Горизонтальное масштабирование

Инстансы stateless: каждый держит свой снимок в памяти и раз в 30 секунд проверяет в БД, не появился ли новый
прогон. Состояния, привязанного к клиенту, нет — инстансы взаимозаменяемы за любым балансировщиком.
