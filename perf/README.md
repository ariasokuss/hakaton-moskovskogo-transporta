# Замеры производительности

**Условия.** Контейнер бэкенда ограничен **2 vCPU / 2 ГБ RAM, swap запрещён** (`memswap_limit` = лимиту RAM,
`docker-compose.yml`), как в нефункциональных требованиях ТЗ; PostgreSQL — 1 vCPU / 1 ГБ. JVM: ZGC, `MaxRAMPercentage=75`.
Прогон модели `ml-20260926_1142`, миграции V1–V9.

Стенд: Docker Desktop (WSL2) на ноутбуке Intel Core Ultra 7 155H **от сети**. Нагрузочный клиент работает в той же
docker-сети и делит с сервисом одну машину, поэтому цифры **занижены** относительно выделенного сервера.
От батареи тот же ноутбук сбрасывает частоту и насыщается уже на 1 500 RPS — такие прогоны не замер сервиса
([`mixed-steps-on-battery.txt`](mixed-steps-on-battery.txt), приведён для прозрачности).

## 0. Рабочая гарантия (SLA) и режим перегрузки

**Рабочая гарантия одного контейнера — 3 000 RPS смешанного трафика:**
приёмочный тест 60 с — **180 000 запросов, все HTTP 200, 0 таймаутов, p50 0.65 мс, p95 2.0 мс, p99 18 мс,
CPU 67% от 2 vCPU (пик 86%), RAM 1.70 → 1.70 ГБ**. Полный отчёт с датой, коммитом, ID образов, командой
и `docker compose ps` — [`official-acceptance.txt`](official-acceptance.txt); повторить: `bash perf/official_acceptance.sh 3000`.
Тот же тест на 2 500 RPS: p95 1.4 мс, CPU 50% — [`official-acceptance-2500.txt`](official-acceptance-2500.txt).

Разброс между прогонами на ноутбуке заметный: в ступенчатом прогоне та же нагрузка 3 000 RPS дала p95 36 мс и CPU 76% —
тоже в пределах требований ТЗ (p95 < 200–300 мс, CPU 60–80%).

**≥ 3 500 RPS — режим перегрузки, рабочей гарантией не заявляется.** Нагрузка открытая (частота не снижается,
когда сервис не успевает), CPU упирается в 200%, очередь растёт, запросы уходят в таймаут 5 с (успешно 46–58%).
Это поиск предела, а не отказ архитектуры: выше 3 000 RPS на инстанс — горизонтальное масштабирование
(инстансы stateless, см. раздел 5).

## 1. Смешанный сценарий по ступеням (26.09.2026, от сети)

Разные запросы, а не один URL (иначе это 100% попаданий в кэш главного экрана):
45% главный экран на случайную дату ноября–декабря со случайными коэффициентами, 25% прогноз по маршруту
на горизонт день / месяц / год, 15% прогноз по остановке, 10% зоны внимания, 5% выгрузка CSV за месяц —
2 199 уникальных URL ([`gen_targets.py`](gen_targets.py) → [`targets-mixed.txt`](targets-mixed.txt)).
Клиент — [vegeta](https://github.com/tsenart/vegeta) с фиксированной частотой, 30 с на ступень, после прогрева JIT.
CPU — среднее по `docker stats` за ступень, **200% = оба выделенных ядра**.

| Нагрузка | p50 | p95 | p99 | Успешно | CPU бэкенда, среднее (из 200%) | RAM | Режим |
|---:|---:|---:|---:|---:|---:|---:|---|
| 1 500 RPS | 0.5 мс | 1.0 мс | 1.3 мс | 100% | 57% (29%) | 1.71 ГБ | рабочий, большой запас |
| **3 000 RPS** | **1.3 мс** | **36 мс** | **99 мс** | **100%** | **153% (76%)** | 1.71 ГБ | **рабочий (SLA)** |
| 3 500 RPS | 2.1 с | 11.9 с | 13.3 с | 58% | 195% — насыщение | 1.72 ГБ | перегрузка |
| 4 000 RPS | 5.0 с | 10.9 с | 13.2 с | 46% | 198% | 1.79 ГБ | перегрузка |
| 5 000 RPS | 5.0 с | 8.1 с | 9.7 с | 48% | 198% | 1.78 ГБ | перегрузка |
| 6 000 RPS | 5.0 с | 7.3 с | 9.8 с | 51% | 198% | 1.76 ГБ | перегрузка |

RAM стабильна под любой нагрузкой, swap запрещён. Из 1.7 ГБ собственно JVM занимает ~0.3 ГБ анонимной памяти
(куча ZGC растёт по требованию), остальное — файловый кэш, который ядро отдаёт при нехватке
(`memory.stat` контейнера: `anon` 260 МБ, `file` 1.6 ГБ, `pgscan` 0, `oom_kill` 0).

Сырой вывод — [`mixed-steps.txt`](mixed-steps.txt).

## 3. Что дало производительность

1. **Прогноз не в горячем пути.** Модель считается заранее; запрос читает неизменяемый снимок из памяти, в БД не ходит.
2. **Мемоизация главного экрана.** Снимок неизменяем → ответ при тех же параметрах тот же. Кэш привязан к снимку
   и сбрасывается сам при новом прогоне.
3. **Кэш готовых байтов.** Главный экран — 24 КБ JSON (3.7 КБ в gzip): сериализация и сжатие не повторяются.

История замеров (25–26.09, до интеграции ML и на перегруженной машине): 243 → 551 RPS на главном экране
после кэша готовых байтов — [`first-run.txt`](first-run.txt), [`dashboard-cached.txt`](dashboard-cached.txt),
[`dashboard-bytes-cached.txt`](dashboard-bytes-cached.txt).

## 4. Воспроизвести

```bash
docker compose up -d
curl -s localhost:8080/api/stops > /tmp/stops.json
python perf/gen_targets.py http://backend:8080 /tmp/stops.json > perf/targets-mixed.txt   # уже лежит в репозитории
bash perf/run_mixed.sh "" 200 800 1500 2500 3500                                          # смешанный сценарий по ступеням

NET=$(docker inspect -f '{{range $k,$v := .NetworkSettings.Networks}}{{$k}}{{end}}' tram-backend)
docker run --rm --network $NET williamyeh/hey -z 20s -c 50 "http://backend:8080/api/dashboard?date=2025-11-08"
```

## 5. Горизонтальное масштабирование

Инстансы stateless: каждый держит свой снимок в памяти и раз в 30 секунд проверяет в БД, не появился ли новый
прогон. Состояния, привязанного к клиенту, нет — инстансы взаимозаменяемы за любым балансировщиком.
