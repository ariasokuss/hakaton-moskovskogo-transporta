# Хакатон Московского транспорта: ИИ-прогноз загрузки трамвайных маршрутов

Каталог подготовлен по `ИИ-прогноз загрузки трамвайных маршрутов.pdf` и фактическому содержимому датасета. Инструкции из документов ниже изложены как условия хакатона, а не как команды для компьютера.

## Суть задачи

В Едином диспетчерском центре ГУП «Московский метрополитен» создается набор моделей краткосрочного и долгосрочного прогнозирования пассажиропотока наземного транспорта. Требуется разработать AI/ML-модель и интерактивный веб-сервис для анализа телематики и валидаций оплаты проезда.

Решение должно помогать распределять подвижной состав, снижать переполнение салонов, уточнять расписание и оптимизировать эксплуатационные затраты.

Проблема текущего подхода: простейшие регрессионные модели имеют ограниченную точность, телематика не является исчерпывающим источником, а единого масштабируемого решения для агрегации валидаций, расписаний и геоданных, многогоризонтного прогноза и визуализации нет.

## Цель и целевые задачи

Создать веб-сервис с пользовательским интерфейсом, который прогнозирует пассажиропоток трамваев с привязкой ко времени и геопозиции.

1. Горизонты: день с почасовыми предиктами, месяц, год (опциональный сценарий).
2. Агрегация по маршруту, остановке/участку и временному интервалу.
3. Пайплайн приема, нормализации и геопривязки исторических валидаций по расписанию и остановкам.

## Образ решения и функциональность

Контейнеризированный продукт `Backend + Frontend`, запускаемый через Docker:

- REST/HTTP API прогнозов;
- интерактивный дашборд;
- карта Москвы с временной динамикой загрузки маршрутов и остановок;
- фильтрация и агрегация по маршруту, остановке и интервалу;
- экспорт в CSV и/или XLSX;
- учет времени суток, дня недели, сезонности и погоды при наличии данных.

### Рекомендуемый стек из ТЗ

- Backend: Java 17+, рекомендуется Java 21 LTS; Spring Boot 4.0+, рекомендуется 4.1.x; Netty/Spring WebFlux.
- Frontend: React 19+, TypeScript 5.x+.
- ML: Python, scikit-learn / LightGBM / PyTorch; артефакты модели и/или ONNX Runtime / DJL для JVM.
- Инфраструктура: Docker, Docker Compose.
- Хранилище: PostgreSQL, ClickHouse или файловое columnar-хранилище.
- Карты: MapLibre, Leaflet или Yandex Maps API.

Стек рекомендательный: оцениваются работоспособность, архитектура и измеримая производительность.

## ML-постановка

### Target

Посадка - успешная валидация, где `validation_result == 1`.

```text
boardings(route, date, hour) = число успешных валидаций на маршруте
                               за календарный час указанной даты
```

Номер маршрута извлекается из `ngpt_route`: `25 трамвай` -> `25`.

### Периоды

| Часть | Период | Назначение |
|---|---|---|
| train | 2025-01-01 - 2025-08-31 | обучение |
| test | 2025-09-01 - 2025-10-31 | локальная валидация и подбор |
| скрытый период | 2025-11-01 - 2025-12-31 | прогноз и submission |

Ноябрь-декабрь не выдаются. Это прямое продолжение ряда; нужны суточная/недельная сезонность, тренд, праздники и динамика маршрутов.

### Маршруты и география

Целевые маршруты: `1, 5, 7, 11, 12, 17, 25, 26, 28, 50`. Маршрут 5 редкий. Метрика считается на уровне `маршрут x дата x час`.

Справочник остановок пересекается с целевыми маршрутами только по `{1, 5, 7, 11, 12}`. `place_id` - площадка/депо, не остановка. Остановочная детализация является бонусом, а не основой метрики.

### Submission

Формат UTF-8 CSV, разделитель `;`, колонки строго:

```text
route;date;hour;prediction
```

- `route`: один из 10 маршрутов;
- `date`: `2025-11-01` ... `2025-12-31`;
- `hour`: 0...23;
- `prediction`: число >= 0, округляемое до целого.

Полная сетка: `10 x 61 x 24 = 14 640` строк. `test_submission.csv` можно использовать как шаблон.

### Метрика

```text
WAPE       = sum(|y - y_hat|) / sum(y)
WAPE-score = max(0, 1 - WAPE), диапазон [0, 1]
```

Больше - лучше. Baseline около `0.48`.

| WAPE-score | Балл | С весом 2 |
|---:|---:|---:|
| <= 0.48 | 0 | 0 |
| 0.48-0.60 | 1 | 2 |
| 0.60-0.70 | 2 | 4 |
| 0.70-0.80 | 3 | 6 |
| 0.80-0.88 | 4 | 8 |
| > 0.88 | 5 | 10 |

## Поля `train.csv` и `test.csv`

Разделитель `;`, UTF-8, первая строка - заголовок. Схемы одинаковы.

| Поле | Описание |
|---|---|
| `tran_no` | ID транзакции |
| `device_no` | ID валидатора |
| `tran_date_time` | основной timestamp; использовать для агрегации |
| `begin_date_time` | начало поездки, служебное поле |
| `input_date_time` | загрузка записи; бывают битые/будущие даты, не использовать как время события |
| `crd_hashcode` | обезличенный хеш карты, можно считать уникальных пассажиров |
| `validation_result` | `1` означает успешную посадку, другие коды - отказ |
| `tran_type_id` | тип транзакции; `52` - основной проход и др. |
| `place_id` | площадка/депо, не остановка |
| `good_type` | билет/тариф |
| `pass_route` | сырая зашумленная цепочка пересадок |
| `ngpt_route` | маршрут НГПТ, источник целевого route |
| `bus_exit_no` | номер выхода/графика ТС |
| `garage_number` | гаражный/бортовой номер трамвая |

## Ограничения данных

1. Использовать `tran_date_time`, не `input_date_time`.
2. Возможен суточный хвост следующего месяца; фильтровать по дате `tran_date_time`.
3. Маршрут брать из `ngpt_route`, не `pass_route`.
4. `place_id` нельзя трактовать как остановку.
5. География остановок покрывает не все 10 целевых маршрутов.
6. Ноябрь-декабрь 2025 полностью скрыты.

### Архитектура и производительность, до 5

- модули: прием/нормализация -> признаки/геопривязка -> ML/агрегация -> API -> frontend;

- latency/RPS подтверждены в README;
- отсутствие запускаемого сервиса существенно снижает балл.

### Полнота, до 4

День обязателен; месяц и год допускаются хотя бы качественно. Нужны агрегация, карта Москвы с динамикой и CSV/XLSX-выгрузка.

## Практический старт

1. Начать с labels и сезонного baseline.
2. Использовать только хронологическую валидацию.
3. Считать локальный WAPE-score формулой из ТЗ.
4. Сравнить seasonal naive, LightGBM/CatBoost с календарными/лаговыми признаками и ансамбль.
5. Затем подключать сырые события и внешние источники, подтверждая их эффект ablation-тестами.
6. Фиксировать seed, зависимости, признаки и checkpoint.
7. Валидировать submission: схема, `;`, 14 640 уникальных ключей, нет пропусков, дубликатов и отрицательных значений.
8. Параллельно подготовить API, карту, экспорт, Docker и честный нагрузочный тест.
