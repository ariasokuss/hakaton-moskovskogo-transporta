# CLAUDE.md — конституция проекта

Проект: **ИИ-прогноз загрузки трамвайных маршрутов**, Хакатон Московского транспорта.
Дедлайн: **27.09.2026, 23:59 МСК**. Исходное ТЗ: `ИИ_прогноз_загрузки_трамвайных_маршрутов.pdf`.

Этот файл — жёстко закреплённые требования организаторов. **Он не обсуждается и не
переигрывается по ходу работы.** Любое отступление — только по явному решению владельца
репозитория, с фиксацией причины в разделе «Отступления».

## 0. Разделение ответственности в команде

| Зона | Кто |
|---|---|
| ML-модели, обучение, тюнинг, WAPE | 2 человека из команды, **параллельно, не мы** |
| Backend-сервисы (API, пайплайн, БД, Docker, инференс-обвязка) | **мы** |
| Frontend (дашборд, карта, UX/UI) | **мы**, приоритет на качество дизайна |

Следствия, которые держим в голове постоянно:
- Контракт с ML-контуром — это **граница между командами**. Зафиксировать письменно и
  рано: формат артефакта модели, формат фич на входе, формат предикта на выходе.
- Мы не блокируемся на ML. Сервис поднимается и отдаёт ответы **на заглушке
  (stub-предикторе)** с первого дня; реальная модель подключается как замена реализации.
- Фронт — не «страничка для галочки». Это наша сильная сторона, и она напрямую кормит
  критерий 4 (дашборд, карта, выгрузка), критерий 5 (бизнес-ценность) и питч (0–10).

## 1. Стек — зафиксирован, альтернативы не рассматриваем

### Backend
- **Java 21 LTS** (ТЗ: Java 17+, рекомендуется 21).
- **Spring Boot 4.x** (ТЗ: 4.0+, рекомендуется 4.1.x).
- **Spring WebFlux поверх Netty** — реактивный стек. Не Spring MVC, не Tomcat.
  Прямое требование ТЗ по пропускной способности, а не вкусовщина.
- Сборка: **Gradle (Kotlin DSL)** или Maven — выбрать один раз и не менять.

### Frontend
- **React 19+**, **TypeScript 5.x+**. JS без типов запрещён.
- Карта: **MapLibre GL** (приоритет) / Leaflet / Yandex Maps API.
- Графики: любая библиотека, но единый визуальный язык по всему дашборду.

**Пользователь — диспетчер**, интерфейс является элементом системы диспетчеризации
и оперативного управления. Кросс-платформенность (монитор диспетчерской + планшет)
обязательна. Три принципа, подробно — в `docs/ui-design-principles.md`:
1. **Оперативность** — переключения мгновенные, без спиннеров на взаимодействии.
2. **Однозначность обозначений** — цифро-буквенный номер маршрута читается при
   любом масштабе и одинаков на карте, в таблице, в графике и в экспорте;
   соответствует мнемосхеме. Цвет и подпись маршрута приходят с бэкенда.
3. **Минимум паразитных действий** — минимум действий, максимум информации;
   любой рабочий вопрос закрывается за одно действие, максимум за два.

Следствия для API (обязательны): композитные ответы «один экран — один запрос»;
справочник представления маршрутов с сервера; все фильтры как query-параметры
(состояние экрана выразимо ссылкой); отклонение от базового уровня считает бэкенд;
экспорт повторяет экран.

### ML-контур
- **Python** (scikit-learn / LightGBM / PyTorch) — зона соседей по команде.
- Инференс: **ONNX Runtime или DJL внутри JVM** — приоритетный вариант, он же лучше
  по latency. Fallback — отдельный Python-сервис в compose.
  **Решение принимается один раз, до начала кодирования API.**

### Хранилище — **PostgreSQL + R2DBC** (зафиксировано 25.09.2026)
ТЗ допускает PostgreSQL / ClickHouse / файловое columnar. Выбран **PostgreSQL с
реактивным драйвером R2DBC**.

Почему не ClickHouse: у нас WebFlux, нужен неблокирующий драйвер. У PostgreSQL это
R2DBC — нативно ложится на реактивный стек. У ClickHouse нормального реактивного
драйвера нет, пришлось бы городить обёртку с отдельным пулом потоков и частично
терять смысл Netty. Объёмы у нас не те, где ClickHouse даёт решающий выигрыш:
сырые валидации агрегируются заранее, а таблица прогнозов обозрима и закрывается
индексами.

### Модель работы с данными — прогнозы предрассчитываются
**Инференс модели не должен находиться в горячем пути HTTP-запроса.** Прогнозы
считаются заранее, батчем, и складываются в БД; API на запрос делает только выборку
и агрегацию. Тогда p95 определяется скоростью БД, а не моделью, и целевые
«сотни RPS при p95 < 200–300 мс» достижимы. Это же обеспечивает stateless-инстансы
и горизонтальное масштабирование.

### 🔴 Граница данных: свои и внешние не смешиваются (зафиксировано 26.09.2026)

**Основная БД содержит только данные организаторов** (`dataset.zip`: валидации, labels,
справочники) и производные от них величины.

**Всё, что подтягивается снаружи** (погода Open-Meteo, производственный календарь,
события Дептранса, баллы пробок), живёт **отдельным слоем** — своими таблицами в своей
схеме (`external.*`) либо отдельным хранилищем, с обязательными полями `source`,
`fetched_at`, `source_url`.

Почему так:
- **воспроизводимость**: прогон на одних данных организаторов должен быть повторим
  без сети и без внешних сервисов;
- **честность перед жюри**: видно, что базовый прогноз построен на основном датасете,
  а внешние данные — только поправки (этого прямо требует README датасета);
- **отказоустойчивость**: внешний источник недоступен → сервис работает на базовом
  прогнозе, коэффициенты по умолчанию = 1. Внешняя сеть не в критическом пути;
- **критерий 2**: на каждый внешний источник нужна ссылка и измеренный эффект —
  их проще предъявить, когда они лежат отдельно и помечены источником.

Смешивать их в одной таблице запрещено. Соединение — только на выдаче, множителем.

Три слоя данных организаторов, не смешивать между собой:
1. **Справочники** — маршруты, остановки, координаты, расписание. Мелкие, читаются
   часто → кандидаты на кэш в памяти.
2. **Исторические валидации, агрегированные** до «остановка × час × пассажиры».
   Вход для обучения и основа baseline.
3. **Прогнозы** — то, что отдаёт API: `(маршрут, остановка, timestamp, горизонт,
   значение)` + **версия модели**, чтобы сравнивать прогоны и не ломать выдачу при
   переобучении.

**Корректирующие коэффициенты** (погода/событие/сезон) применяются **поверх**
сохранённого прогноза при выдаче — дешёвое умножение, пересчёт мгновенный.
Ровно то, что требует критерий 2в: ползунок в интерфейсе → сразу новый прогноз.

## 2. Структура проекта — модульное разделение обязательно

ТЗ (критерий 3) прямо требует **читаемого разделения на модули**:

```
приём/нормализация данных → признаки/геопривязка → ML-прогноз/агрегация → API → frontend
```

Это не рекомендация к стилю, это оцениваемый пункт. Каждый этап — отдельный,
именованный, изолированный модуль. Границы между ними — явные интерфейсы, а не
сквозные вызовы.

```
/backend          Java 21 + Spring Boot 4 + WebFlux
  ingest/         приём и нормализация валидаций
  features/       признаки, геопривязка по остановкам и расписанию
  forecast/       вызов модели, агрегация предиктов
  api/            REST-контроллеры, DTO, обработка ошибок
  export/         CSV / XLSX
/frontend         React 19 + TypeScript 5
/ml               артефакты модели + код обучения/инференса (зона ML-команды)
/docs             схема архитектуры, реестр внешних источников, область применимости
/perf             сценарии нагрузочного теста и результаты замеров
docker-compose.yml
README.md
```

## 3. Функционал — минимум, ниже которого не опускаемся

| Требование | Статус |
|---|---|
| Прогноз на **день, с разбивкой по часам** | **обязателен** |
| Прогноз на **месяц** | обязателен, хотя бы качественно |
| Прогноз на **год** | опционально, хотя бы качественно |
| Агрегация по **маршруту** | обязательна |
| Агрегация по **остановке / участку** | обязательна |
| Агрегация по **интервалу времени** | обязательна |
| **Интерактивный дашборд с картой Москвы** | обязателен |
| Динамика пассажиропотока по времени и точкам маршрута | обязательна |
| **Экспорт CSV и/или XLSX** | обязателен |
| Учёт времени суток, дня недели, сезонности, погоды | обязателен |
| **Корректирующие коэффициенты в интерфейсе** с немедленным пересчётом | +1 балл, делаем |
| Воспроизводимый пайплайн приёма данных | +1 балл, делаем |

### Агрегация — час является минимальной единицей
**Минимальный интервал прогноза и хранения — один час.** Модель выдаёт почасовые
предикты; всё остальное (день, неделя, месяц, год, произвольный интервал) —
**агрегация вверх** по этой сетке, а не отдельные модели. Сетка прогноза
`маршрут × дата × час` — единственный источник истины, ниже часа не спускаемся.

### Часы работы и технические валидации
Валидации вне часов работы маршрута — технические (проверка валидатора), в
пассажиропоток не входят. Практика по данным (см. `docs/data-anomalies.md`):
- техническим шумом является **только часы 2 и 3** (0.002% объёма, спорадически);
- **часы 0, 1, 4 — реальная работа**, фильтровать их нельзя;
- **окно работы задаётся по маршруту**: 1 и 28 — с 5 ч, 25 — с 6 ч, остальные 0–23.

Фильтрация применяется при **оценке уровня и суточных профилей**. В сабмите сетка
остаётся полной (14 640 строк), ночные часы предсказываются близкими к нулю.

### Округление прогноза
`prediction` — целое число ≥ 0, **округление к ближайшему целому** (half-up).
Округление выполняется **только на границе выгрузки** (submission / экспорт).
Внутри сервиса и в БД прогноз хранится как дробное значение: округлять до
применения корректирующих коэффициентов нельзя, иначе ошибка накапливается
на каждом множителе.

### Адаптивность сервиса
Режимы маршрута (работы на путях, приостановка, смена уровня) — **данные, а не
константы в коде**. Сервис должен позволять задать интервал аномалии и пересчитать
выдачу без пересборки: таблица режимов + коэффициент на интервал.

### REST API — контракт
API обязано отдавать прогноз по всем четырём параметрам:
**маршрут · остановка/участок · интервал времени · горизонт (day | month | year)**.

Плюс: эндпоинт экспорта, эндпоинт корректирующих коэффициентов, health-check.

## 4. Нефункциональные требования — с числами

- **Производительность:** один контейнер **2–4 vCPU / 2–4 ГБ RAM**, держит
  **сотни RPS** при **p95 < 200–300 мс**, утилизация CPU **60–80%** с запасом,
  RAM стабильна **без swap**.
- **Масштабируемость:** совместимость с горизонтальным масштабированием.
  Практически: инстансы **stateless**, всё состояние — в БД/кэше, никакой локальной
  сессии и никакого локального файлового состояния.
- **Эффективность:** оптимальное использование CPU/RAM в рамках одного контейнера.
- **Надёжность:** корректная обработка ошибок API, **понятные сообщения пользователю**.
  Единый формат error-ответа — **RFC 9457 (Problem Details)**, поддерживается Spring
  из коробки. Никаких голых стектрейсов наружу.
- **Расширяемость** за счёт внешних данных: погода, трафик, стройки, новые маршруты.

### 🔴 Железное правило README
**В README ОБЯЗАТЕЛЬНО указать замеры производительности (latency / RPS).**
В ТЗ это написано капслоком. Жюри **своего нагрузочного теста не проводит** и оценивает
критерий 3 **по нашим заявленным цифрам**; честная оценка с подтверждением засчитывается.
Нет цифр — нет баллов.

Отсюда: замеры собираем **по ходу работы, в `/perf`**, а не в последнюю ночь.

### 🔴 Железное правило запускаемости
**«При отсутствии запускаемого сервиса балл существенно снижается.»**
Поэтому `docker compose up` поднимает работающее решение **с первого дня**, пусть даже
на заглушках. Запускаемость приоритетнее полноты и красоты кода.

## 5. Внешние источники — только со ссылками

Критерий 2а даёт **до 4 баллов**, по 1 за каждый использованный и подтверждённый
эффектом источник:
1. дорожный трафик / загруженность улиц;
2. погодные условия (температура, осадки);
3. сезонность и календарь (выходные, праздники РФ/Москвы, каникулы);
4. прочие факторы (события, новости, перекрытия, ремонты).

**Обязательное условие: на каждый источник — рабочая ссылка или способ получения.
Источник без ссылки не засчитывается.** Реестр источников ведём в `/docs` сразу, как
только источник появился в коде.

## 6. Критерии оценки — куда бьём

| № | Критерий | Баллы | Наша зона |
|---|---|---|---|
| 1 | Качество прогноза (WAPE-score) | 0–10 (×2) | ML-команда |
| 2 | Данные, внешние источники, область применимости | 0–8 | пайплайн и коэффициенты — наши |
| 3 | **Архитектура и производительность** | 0–5 | **полностью наша** |
| 4 | **Полнота функциональности** (горизонты, агрегация, карта, выгрузка) | 0–4 | **полностью наша** |
| 5 | Бизнес-ценность и применимость | 0–2 | наша, через дашборд и питч |
| 6 | Полуфинальный питч | 0–10 | общая, демо — наше |

**Итого максимум по этапам 1–2: 39 баллов.**

WAPE-score = `max(0, 1 − Σ|y − ŷ| / Σy)`, больше — лучше.
Baseline **≈ 0.48** — «пол», который надо превзойти. Максимум балла — при **> 0.88**.

Из 39 баллов **напрямую в нашей зоне — 9 (критерии 3 и 4)**, плюс весомая часть
критериев 2, 5 и питча. Это надо забирать целиком: в отличие от WAPE, здесь результат
полностью контролируем.

## 6б. Формат питча (0–10 баллов)

**5 минут выступления + 5 минут ответов жюри, формат презентации.**

Следствия для разработки:
- на демо сервиса есть **60–90 секунд**, не больше. Сценарий один, отрепетированный,
  без блужданий по интерфейсу;
- демо-состояние открывается **по прямой ссылке** — это ещё одно обоснование
  требования «все фильтры в URL». Никаких «сейчас я настрою фильтры»;
- никакой загрузки данных на глазах у жюри: экран должен быть готов сразу;
- **записанный скринкаст как резервный вариант** на случай отказа сети или демо;
- к блоку вопросов готовы заранее: цифры WAPE, таблица ablation по внешним
  источникам, замеры latency/RPS, пределы применимости модели. Это ровно те
  четыре темы, по которым спросят.

## 8. Правила работы над кодом

- Любая задача сверяется с этим файлом до начала реализации.
- Не менять стек, не менять структуру модулей, не выкидывать пункты из раздела 3.
- Сервис всегда остаётся запускаемым: не ломать `docker compose up` ради рефакторинга.
- Ошибки API — всегда с человекочитаемым сообщением (оцениваемое требование).
- Внешний источник данных добавлен в код → сразу ссылка в реестр `/docs`.
- Замер производительности сделан → сразу в `/perf` и в README.
