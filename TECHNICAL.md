# Пантограф — техническое описание проекта

Документ описывает, как устроено решение: из каких частей оно состоит, на чём написано, как между собой
разделены задачи и какие инженерные решения приняты. Пользовательское описание, запуск и результаты — в [README.md](README.md),
локальный запуск — в [LOCAL_SETUP.md](LOCAL_SETUP.md).

Задача хакатона Московского транспорта: прогноз посадок в трамваи `boardings(route, date, hour)` на 01.11–31.12.2025
и веб-сервис для диспетчера с картой, агрегацией, выгрузкой и корректирующими коэффициентами.
Исходное ТЗ — [`docs/ТЗ — ИИ-прогноз загрузки трамвайных маршрутов.pdf`](docs/).

---

## 1. Разделение работы

Проект разделён на три контура с явными границами. Контуры разрабатывались параллельно и связаны только файловым контрактом.

| Контур | Задачи | Результат |
|---|---|---|
| **ML** | анализ данных, приём сырых валидаций, модель прогноза, валидация, внешние источники, замер их эффекта | ноутбук `ml/pantograph_best_colab.ipynb`, веса `ml/artifacts/`, артефакты прогноза `data/forecast/` |
| **Backend** | приём данных при старте, хранение, агрегация прогноза, отклонения, API, экспорт, отчёт, фоновая загрузка внешних источников, замеры производительности | сервис `backend/` (Java), схема БД, `perf/` |
| **Frontend** | рабочее место диспетчера: карта, графики, панели, поправки, выгрузки | приложение `frontend/` (React) |
| **Аналитика и документация** | сверка с ТЗ, реестр источников, область применимости, матрица доказательств | `docs/`, README |

### Контракт между ML и сервисом

Сервис не вызывает модель: прогноз считается заранее и передаётся файлами. Формат зафиксирован в `ml/artifacts/ml_contract.json`.

| Файл | Формат | Назначение |
|---|---|---|
| `forecast_hourly.csv` | `route;date;hour;pred;model_version` — дробное значение, без округления | почасовой прогноз ноябрь–декабрь |
| `forecast_year_monthly.csv` | `month;route;boardings;low;high;source;model_version` | горизонт «год», помесячно с интервалом |
| `coefficients.json` | коэффициенты поправок, измеренные эффекты, ссылки на источники | ползунки и фильтры в интерфейсе, `GET /api/coefficients` |
| `ml_contract.json` | модели, признаки и их порядок, категории, формулы target и смешивания | инференс вне ноутбука |
| `submission_latest.csv` | `route;date;hour;prediction` | сабмит в формате организаторов |

Новая версия модели (другой `model_version`) импортируется сервисом как новый прогон; старые прогоны сохраняются.
Согласованность проверяет `tools/verify_artifacts.py`: файл ML = БД = выгрузка сервиса.

## 2. Стек

| Слой | Технологии и версии |
|---|---|
| Backend | Java 21 (LTS), Spring Boot 4.1.1, Spring WebFlux на Netty (реактивный стек), Spring Data R2DBC, Flyway, Actuator, Bean Validation; FastExcel (XLSX), OpenPDF (PDF-отчёт) |
| Хранилище | PostgreSQL 17, реактивный драйвер R2DBC; миграции Flyway V1–V11 |
| Frontend | React 19, TypeScript, Vite 8, MapLibre GL 5; шрифты Onest, JetBrains Mono |
| ML | Python 3.10+, pandas, NumPy, SciPy, scikit-learn, LightGBM 4, DuckDB (приём сырых данных), Jupyter / Google Colab |
| Инфраструктура | Docker, Docker Compose; образы `gradle:8.14.3-jdk21` → `eclipse-temurin:21-jre-alpine`, `node:24-alpine` → `nginx:1.29-alpine`, `postgres:17-alpine` |
| Геоданные | OpenStreetMap (трассы, остановки, улицы вдоль трасс), подложка OpenFreeMap |

Выбор PostgreSQL + R2DBC: неблокирующий драйвер нативно работает с WebFlux; объём данных (агрегаты и прогноз)
не требует колоночного хранилища, запросы закрываются индексами.

## 4. Архитектура

### Поток данных

```
приём и нормализация  →  признаки и геопривязка  →  прогноз и агрегация  →  API  →  интерфейс
(ingest_raw.py,          (ноутбук,                  (модель в ноутбуке,       (backend/api,   (frontend)
 backend/ingest)          backend/features)          backend/forecast)         backend/export)
```

Схема модулей, путь запроса и развёртывание — [docs/architecture.md](docs/architecture.md).

### Ключевые решения

| Решение | Как реализовано | Зачем |
|---|---|---|
| Прогноз предрассчитывается | модель считает прогноз батчем, сервис импортирует его при старте и держит сетку в памяти | в пути HTTP-запроса нет ни модели, ни БД: p95 — единицы миллисекунд |
| Прогоны иммутабельны | `core.forecast_run` со статусом, горизонтом и версией модели; выдача переключается атомарно | сравнение версий, выдача не ломается при переобучении |
| Асинхронный годовой прогон | горизонт «год» считается в фоне и не блокирует короткий | быстрый старт сервиса |
| Мультипликативная модель | `ŷ = база × K_calendar × K_weather × K_regime × K_incident × K_season × K_user`; коэффициенты хранятся отдельно | поправки в интерфейсе пересчитываются мгновенно, без модели |
| Граница данных | данные организаторов — схема `core.*`; внешние — схема `external.*` с полями `source`, `source_url`, `fetched_at` | воспроизводимость без сети, прозрачность источников |
| Сеть вне критического пути | сервис поднимается на снимке данных из репозитория, внешние источники обновляются фоном с таймаутом | недоступный источник → коэффициент 1, сервис работает |
| Режимы маршрутов — данные | ремонты, отмены, смены уровня — строки `core.route_regime` с датами и ссылкой | новый режим учитывается без пересборки |
| Stateless-инстансы | состояние — в БД; инстанс раз в 30 с проверяет новый прогон | горизонтальное масштабирование за балансировщиком |
| Состояние экрана в URL | все фильтры — query-параметры | картину экрана передают ссылкой; демо открывается готовым |

## 5. Данные

### Слои данных организаторов

| Слой | Содержимое | Использование |
|---|---|---|
| Справочники | маршруты, остановки, порядок остановок, расписание | представление маршрутов (номер, цвет, часы работы) |
| Факт | агрегат валидаций `route × date × hour` (labels или `data/load/load_hourly.csv`) | обычный уровень, факт на графике |
| Прогноз | прогоны модели с версией | выдача API |

### Правила обработки

| Правило | Основание |
|---|---|
| Время события — `tran_date_time` | `input_date_time` содержит битые даты |
| Маршрут — из `ngpt_route` | `pass_route` — зашумлённая цепочка пересадок |
| `place_id` не используется как остановка | это площадка или депо |
| Минимальная единица прогноза и хранения — час | день, месяц, год — агрегация вверх по той же сетке |
| Технические часы — 2 и 3 | 0.002% объёма; в форме суток не участвуют, прогноз 0 |
| Окно работы — по маршруту | определено по посадкам сентября–октября |
| Округление half-up — только на выгрузке | внутри сервиса значения дробные, ошибка не накапливается на множителях |
| Нагрузка на вагон — коды 1 и 90 | код 90 — пересадка без списания; целевая величина — только код 1 |

Аномалии данных и режимы маршрутов — [docs/data-anomalies.md](docs/data-anomalies.md).

## 6. ML-контур

| Компонент | Реализация |
|---|---|
| Профиль | форма суток по типу дня (пн–чт, пт, сб, вс; праздник → вс, рабочая суббота → будни) за 16 недель, уровень — медиана за 3 недели; летние недели исключены |
| LightGBM | 9 моделей: горизонты обучения 3/14/28 дней × seed 42/43/44; прямой прогноз из точки прогноза; целевая — отношение к профилю, L1 |
| Смешивание | вес ML 0.6 на днях 1–21 горизонта, 0.2 дальше; уровень маршрута на горизонте привязан к профилю |
| Поправки | календарь, погода (дождь в тёплую погоду, первые 7 дней, архив прогнозов), режимы маршрутов, сбои, сезонный рост уровня 1.03 |
| Валидация | 6 хронологических фолдов (горизонт 19–61 день), только прошлые данные; тест на утечку; потоковый бэктест с еженедельным переобучением; проверка гипотез по CV |
| Результат | WAPE-score 0.89731 на скрытом периоде ноябрь–декабрь |

Подробнее — [ml/README.md](ml/README.md), внешние источники и их эффект — [ml/EXTERNAL_DATA.md](ml/EXTERNAL_DATA.md),
область применимости — [docs/model-applicability.md](docs/model-applicability.md).

## 7. API

REST, все методы — `GET`, кроме запуска прогона; фильтры — query-параметры. Полный список — README, раздел 9, и `GET /` сервиса.

| Параметр ТЗ | Параметр API |
|---|---|
| маршрут | `route` |
| остановка / участок | `stop` |
| интервал времени | `from`, `to`, `granularity` |
| горизонт | `horizon = day \| month \| year` |
| корректирующие коэффициенты | `kWeather`, `kEvent`, `kSeason`, `kTraffic`, `kManual` |

Ошибки — RFC 9457 (Problem Details), сообщения на русском, без трассировок стека: 400 — неверный параметр,
404 — дата или маршрут вне области прогноза (с перечнем доступных), 503 — прогноз ещё не загружен.

## 8. Нефункциональные требования

| Требование ТЗ | Результат |
|---|---|
| Один контейнер 2–4 vCPU / 2–4 ГБ RAM | backend ограничен 2 vCPU / 2 ГБ в `docker-compose.yml` |
| Сотни RPS при p95 < 200–300 мс | 3 000 RPS при p95 2.0 мс, 0 ошибок (приёмочный тест 60 с) |
| CPU 60–80% с запасом | 67% от 2 vCPU на 3 000 RPS |
| RAM стабильна, без swap | 1.70 ГБ, swap запрещён |
| Горизонтальное масштабирование | stateless-инстансы, состояние в БД |
| Корректные ошибки API | RFC 9457, понятные сообщения |

## 9. Качество и проверки

| Проверка | Команда | Что подтверждает |
|---|---|---|
| Модульные тесты бэкенда | `cd backend && gradle test` | агрегация час → день → месяц, коэффициенты, горизонты, ошибки, экспорт и округление, парсеры |
| Сверка артефактов | `python tools/verify_artifacts.py` | прогноз ML = БД = выгрузка сервиса = сабмит |

| Веса модели | `python ml/load_models.py` | 9 моделей загружаются, признаки совпадают с контрактом |

| Нагрузочный тест | `bash perf/official_acceptance.sh` | 3 000 RPS в требованиях ТЗ |
| Тест на утечку | ячейка ноутбука | прогноз не зависит от данных после точки отсечки |
